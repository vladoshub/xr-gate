XR Gate в Docker: TCP runtime

Папка docker/ в корне репозитория; все команды ниже выполняются из неё. Комплект для XR Gate, релиз v2.3.0, Ubuntu 24.04, Linux x64 / x86-64-v3 (AVX2). Исходники проекта не меняются. Docker скачивает готовый runtime и Mercury-модели с GitHub, проверяет SHA-256 из release.lock.json, устанавливает зависимости из того же релиза. Компиляции XR Gate нет.

Русский · English. Откройте START-HERE.html для выбора языка.

Windows: инструкция Docker Engine в WSL.

Что запускается

Один контейнер с обычным xr_client, capture, Basalt, Mercury и runtime_adapter. Между ними сохраняются штатные SHM-каналы. У runtime_adapter включён дополнительный сервер приложений: JSON Lines, протокол xr_gate_app_v1, TCP 45810.

Соединение Адрес
Приложение Linux/Windows → runtime 127.0.0.1:45810
Прослушивание внутри контейнера 0.0.0.0:45810
Публикация Docker на хосте только 127.0.0.1:45810
Видео TCP, если явно включить только 127.0.0.1:45700

Внутренний bind на 0.0.0.0 нужен для перенаправления Docker. Доступ с LAN не включается. Используется обычная bridge-сеть; --network host, --privileged и публикация UDP не нужны. Для localhost требуется Docker Engine 28+: в старых версиях Docker была особенность доступа из того же L2-сегмента.

SteamVR-драйвер не собирается, не регистрируется и не запускается. Уже находящиеся в upstream-архиве файлы остаются в образе; Windows-драйвер в этот комплект не входит.

Быстрый запуск на Linux

Нужны локальный Docker Engine 28+, Compose plugin, Python 3 и подключённый XREAL Air 2 Ultra. Целевой хост установочного скрипта — Ubuntu 24.04 x64. Другой Linux-хост с подходящим Docker может использовать тот же образ.

Распакуй архив, открой каталог xr-gate-docker и выполни:

chmod +x xr-gate scripts/*.sh image/*.sh
# Если Docker Engine и зависимости USB/Bluetooth ещё не установлены:
sudo bash scripts/install-engine-ubuntu.sh

cp .env.example .env
sudo ./xr-gate build
sudo ./xr-gate check-image
sudo ./xr-gate doctor
sudo ./xr-gate run

Сборке образа нужен интернет: GitHub releases и Ubuntu/Docker package repositories. ZIP не содержит многомегабайтные бинарники; они загружаются при сборке. Для другого релиза нужно осознанно обновить lock-файл, image tag и проверить совместимость.

run запускает контейнер в текущем терминале с stdin и TTY. Видны меню и консоль xr_client; работают его обычные команды. Меню XREAL из релиза сохранено. Для использования текущего режима дисплея выбери соответствующий пункт, либо:

sudo ./xr-gate run -- --prestart-option current

Не закрывай камеры и выполни подсказки startup gate. TCP-сервер запускается на этапе старта runtime_adapter, после готовности предыдущих сервисов. Проверять порт до этого этапа рано.

Во втором терминале:

python3 scripts/tcp_probe.py

Этот тест проверяет hello и получение кадра протокола. Наличие кадра ещё не означает корректный трекинг: приложение должно учитывать pose_valid, tracking status и признаки доступности рук.

Консоль и фон

sudo ./xr-gate up        # Фоновый запуск; меню ждёт ввода
sudo ./xr-gate console   # Подключить stdin/stdout существующего xr_client
sudo ./xr-gate logs      # Только просмотр stdout/stderr
sudo ./xr-gate stop      # Штатная остановка, затем удаление контейнера

Для отключения терминала без остановки контейнера нажми Ctrl+P, затем Ctrl+Q. Ctrl+C в интерактивной консоли предназначен для остановки. Обычный docker compose up не передаёт stdin так, как интерактивный run; для ввода используй console.

Контейнер называется xr-gate. Можно также подключиться через docker attach --sig-proxy=false xr-gate. Одновременно редактировать консоль из нескольких терминалов не следует.

Логи сервисов сохраняются в logs/, где релизный конфиг использует стандартный /tmp/xr_backend_client_logs. Пользовательский log_dir в другом месте потребует своего mount. Настройки контроллеров внутри контейнера хранятся в Docker volume xr-gate_controller-state; stop этот volume не удаляет.

Конфиги с хоста

Без пользовательских файлов запускается неизменённый xreal_ultra.json из релизного архива. Capture, calibration, tracking и остальные значения также остаются релизными. Добавляются только переменные включения TCP; при отдельном включении видео — его TCP-output.

Файл на хосте Действие
config/xr_client.json Используется вместо выбранного релизного профиля
config/override_controller.json Копируется в CONFIG_PATH сервиса контейнера при старте: Gear VR — gearvr.json, evdev — default.json
.env Параметры Docker-комплекта: порты, USB, пути, профиль

Каталог config монтируется read-only. Экспортировать исходные конфиги для редактирования:

sudo ./xr-gate export-configs
# Команда создаёт exported-configs/; существующий каталог не перезаписывает.
cp exported-configs/xr_client/xreal_ultra.json config/xr_client.json

Оба override необязательны и независимы. После изменений перезапусти контейнер. Можно указать другой каталог через XR_CONFIG_DIR в .env, включая абсолютный путь; имена файлов внутри остаются прежними. Простые литеральные KEY=value, без shell-подстановок; пути с пробелами заключай в кавычки.

Для контроллера по-прежнему требуется подходящая конфигурация сервиса в xr_client.json, включая PROVIDERS. Само наличие override_controller.json не меняет провайдер и не запускает сервис. Примеры BLE, evdev и обучение описаны в docs/CONTROLLERS.ru.md.

Если override-файл контроллера есть, его содержимое заново копируется при каждом старте. Если его убрать, используется последнее состояние из volume. Для полного сброса контроллера удали нужный default.json или gearvr.json внутри работающего контейнера через shell, предварительно сохранив нужную калибровку.

USB XREAL

По умолчанию выбирается только VID:PID 3318:0426. Скрипт ищет связанные /dev/video*, /dev/hidraw* и конкретный узел /dev/bus/usb/BBB/DDD. Весь /dev или все USB-устройства не передаются.

Первый UVC capture node устройства (sysfs index 0) отображается в /dev/video0 контейнера: штатный capture-конфиг продолжает работать, даже если на хосте очки оказались /dev/video8. Можно выбрать конкретную камеру через XR_CAMERA_DEVICE=/dev/video8. Она должна относиться к указанному VID:PID. Результат отображения виден в doctor.

После переподключения USB, сна Windows или повторного usbipd attach останови и заново запусти контейнер. Docker привязывает устройства при создании; скрипт заново определит актуальные номера. docker restart не обновляет эти mappings.

Bluetooth

USB Bluetooth подключается к Linux-хосту; на Windows он сначала передаётся в Ubuntu WSL через usbipd. BlueZ работает на этом Linux-хосте, а контейнер получает его system D-Bus socket при XR_BLUETOOTH=1. Так Gear VR BLE использует физический адаптер через свой штатный transport.

Это рабочая архитектура комплекта: отдельный bluetoothd внутри контейнера не запускается. Ядро и драйвер btusb в любом случае принадлежат Linux/WSL. Pairing и trust выполняются в BlueZ хоста, сохраняются там и доступны override_controller через D-Bus. Подробности — в инструкции контроллеров.

Видео

По умолчанию наружу опубликован только TCP приложений. Стереовидео не входит в JSON-протокол runtime_adapter. Capture-изображения внутри контейнера используются для VIO/hand tracking независимо от внешнего просмотра.

Если нужен отдельный видеоклиент, выставь XR_VIDEO_TCP=1 в .env, затем заново запусти контейнер. Появится 127.0.0.1:45700; у xr_video будет VIDEO_OUTPUT=both. Сам backend сохраняет штатное управление: в дефолтном профиле включается/выключается через консольную команду 6. Для подключения нужен клиент бинарного XR video TCP протокола, например tools/xr_video_tcp_client.py из соответствующего релиза/репозитория. Это не H.264/RTSP и не поток отрисовки SteamVR.

Диагностика

sudo ./xr-gate doctor
sudo ./xr-gate config       # Рендер базового Compose без hardware mappings
sudo ./xr-gate shell        # Bash в уже работающем контейнере
sudo ./xr-gate logs
lsusb
ls -l /dev/video* /dev/hidraw*
sudo modprobe uvcvideo
sudo modprobe hid_generic
sudo modprobe btusb

doctor проверяет локальный Engine, версию, устройства и, если включён Bluetooth, BlueZ/D-Bus. Нужен Engine той же Linux-системы, где видны USB-узлы. Remote Docker, rootless Docker и Docker Desktop в этом сценарии скрипт отклоняет.

Если отсутствуют UVC/HID/HCI, сначала исправь драйвер/USB-проброс на хосте. Если capture работает, но gate не проходит, проверь освещение, стабильность очков и логи. Образ использует калибровку конкретного устройства из релиза; собственную калибровку подключай через свой xr_client/device/tracking профиль и дополнительные mounts при необходимости.

Фактический объём проверки этого комплекта и ограничения окружения — в docs/VALIDATION.md. Источники и зафиксированные версии — в docs/SOURCES.md.

SteamVR в Windows

Windows-драйвер собирается отдельным job CI после применения сопровождающего патча. Скачайте artifact xr-gate-steamvr-windows-x64, распакуйте 60Hz-direct и выполните Install-Driver.bat в его папке xr_tracking. При работающем контейнере проверьте Test-TCP.bat, затем запустите SteamVR. Полная инструкция, SBS, Direct Mode и удаление. Direct Mode требует проверки с вашим GPU/очками; передача USB в контейнер не передаёт DisplayPort-видео.

XR Gate in Docker: TCP runtime

Русский · English · Offline guide

This is the repository-root docker/ directory. Run the commands below from this directory. The image downloads pinned XR Gate v2.3.0 Ubuntu 24.04 x64 runtime and separate Mercury models from GitHub, checks SHA-256 and uses the release's dependency installer. It does not compile XR Gate. The release needs an AVX2 / x86-64-v3 CPU.

Windows setup: Docker Engine inside Ubuntu WSL. Controller setup: Gear VR / VR-PARK.

Architecture and localhost ports

The container runs the normal xr_client console, capture, Basalt, Mercury and runtime adapter. Internal streams retain their normal SHM transport. Application TCP is enabled at port 45810, protocol xr_gate_app_v1, JSON Lines.

Connection Address
Windows/Linux host application → runtime 127.0.0.1:45810
Container listener 0.0.0.0:45810 inside its private network namespace
Optional camera-video client 127.0.0.1:45700 when explicitly enabled

Compose publishes on host 127.0.0.1 only. Use regular local Docker Engine 28+ in the same Linux/WSL system that owns the USB nodes. Docker Desktop, remote/rootless engines are not supported by this USB workflow. The scripts do not open LAN ports or use host networking.

First run on Linux

Install Docker Engine and its Compose plugin if needed:

sudo bash scripts/install-engine-ubuntu.sh

From docker/:

cp --no-clobber .env.example .env
sudo ./xr-gate build
sudo ./xr-gate check-image
sudo ./xr-gate doctor
sudo ./xr-gate run

Connect XREAL before the hardware check/run. Keep the resulting xr_client console open, complete its startup gate and display-mode prompts. On WSL, use the current display mode if SBS is already configured in Windows/on the glasses. In another terminal:

./xr-gate check-tcp

For a background container, use sudo ./xr-gate up, then sudo ./xr-gate console. Stop with Ctrl+C in the running console or sudo ./xr-gate stop. Use sudo ./xr-gate logs or sudo ./xr-gate shell for logs/an interactive shell. console uses Docker's attach mechanism; normal Docker detach keys are Ctrl+P then Ctrl+Q.

Release defaults and host configuration

Without overrides, the container uses the release's xreal_ultra profile. The entire config/ directory is mounted read-only. Optional files:

Host path Effect
config/xr_client.json Replaces the selected client profile
config/override_controller.json Copied to the override service's CONFIG_PATH inside the container
.env Docker ports, USB IDs, paths, profile and optional features

For Gear VR, CONFIG_PATH is normally ~/.config/xr_tracking/override_controller/gearvr.json; ordinary evdev/VR-PARK uses default.json. A differing old destination is backed up. Controller state is persisted in a named volume. An active host override is copied again on every startup: export registration/training results back to it before restarting, as described in the controller guide.

Export release templates without overwriting an existing export directory:

sudo ./xr-gate export-configs
cp --no-clobber exported-configs/xr_client/xreal_ultra.json config/xr_client.json

Edit only the needed fields in that copied profile. A controller override alone does not select providers or enable the service. Restart the container after configuration changes. Set XR_CONFIG_DIR in .env for another host config directory. Use literal KEY=value entries, quote paths containing spaces, and avoid shell expressions.

XREAL USB

The default selector is 3318:0426. The helper passes only that device's video/HID/raw-USB nodes, not all of /dev or every USB device. Its first UVC capture node maps to /dev/video0 inside the container, preserving the release profile even if the host uses /dev/video8. Set XR_CAMERA_DEVICE to select a specific capture node of the same USB identity.

After reconnecting USB, Windows sleep, or usbipd attach, stop and recreate the container with this helper. docker restart does not refresh device mappings. The kernel/drivers belong to the Linux/WSL host; missing UVC/HID nodes must be fixed there first.

Bluetooth

BlueZ runs on the Linux host. On Windows, forward a dedicated USB Bluetooth dongle into Ubuntu WSL. Pair/trust controllers through the host's bluetoothctl, then set XR_BLUETOOTH=1 in .env. The container accesses BlueZ through the mounted system D-Bus socket. It does not run another bluetoothd.

For ordinary evdev devices, explicitly list only the required event nodes in XR_INPUT_DEVICES, for example /dev/input/event12,/dev/input/event13. Recreate the container if node names change. Windows XInput/DirectInput access alone does not create Linux event nodes.

Optional stereo camera video

By default only application TCP is published. For a separate binary video client, set XR_VIDEO_TCP=1 in .env, then recreate the container. This publishes 127.0.0.1:45700 and selects VIDEO_OUTPUT=both. The video backend still follows the release profile's console control, normally command 6. Use XR Gate's binary stereo-video client; this is not RTSP/H.264 and does not carry the SteamVR game's rendered display.

Windows SteamVR driver

The patched CI separately builds artifact xr-gate-steamvr-windows-x64. Extract its 60Hz-direct ZIP, close SteamVR and run Install-Driver.bat in the inner xr_tracking folder. With this container running, run Test-TCP.bat, then start SteamVR. See the complete Windows/SBS/Direct Mode guide. Actual Direct Mode support depends on the XREAL display/GPU/video connection.

Do not start direct WSL XR Gate and this container on the same host TCP port at the same time. The Windows driver defaults to 127.0.0.1:45810.

Diagnostics and validation

sudo ./xr-gate doctor
sudo ./xr-gate config
sudo ./xr-gate logs
lsusb
ls -l /dev/video* /dev/hidraw*
bluetoothctl list
rfkill list
sudo modprobe uvcvideo
sudo modprobe hid_generic
sudo modprobe btusb

The helper checks the local Engine, USB nodes and, when enabled, BlueZ/D-Bus. Tracking issues after the startup gate require checking light, calibration and release logs. Configurations are from the pinned release, not a new calibration for every physical device. Tests/limits are listed in docs/VALIDATION.md; the actual Docker daemon, Windows/WSL, USB/Bluetooth and GPU path require hardware validation. No remote CI run or publication is performed by this patch delivery.
